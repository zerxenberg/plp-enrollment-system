# Student Portal enrollment, timetable and legacy recovery

**Scope:** fictional PROJECT_ONLY 2026 student cohort. October 27, 2026.

## Verified before the change

Live Supabase contained 600 placed project students in 11 programs and all four year levels, 61 `READY_PROJECT` validated blocks containing 599 students, 427 finalized project subject sections in `PLANNED` state, and one student in an unvalidated draft block. None of those 427 sections was `OPEN`, while authenticated subject registration requires a `FINALIZED` plus `OPEN` section. Approved academic timetables were therefore visible but not eligible for submission; the draft block must remain unactivated.

The protected Registrar published eight historical BSIT-2A subject workbooks with 96 accepted PROJECT_ONLY grades. Student 25-50001 (Miguel Marie Garcia) has eight accepted previous results and seven academically eligible current semester subjects. His original October 24, 2026, `CONFIRMED_SIMULATION` was created without any immutable `project_phase8_enrollment_subject_snapshots`. A demonstration COR must not be forged from the live timetable. There were eight institutional academic results and eleven institutional enrollments, both unchanged.

## Implemented changes

The Student Dashboard and Current Enrollment module now show separate accepted project academic evidence, official academic evidence, prospective subjects, registered subjects, confirmed records, and verified estimated fees. The prepared table shows `Unit Fee` at the database verified classroom rate of ₱100 per unit and a total below the table. The four requested generic notices are removed; concise actionable recovery and validation warnings remain. The Student Class Schedule now displays the verified proposed assigned block timetable as **proposed**, including subjects, instructors, rooms, days and times, before enrollment confirmation. Only the guarded Registrar COR snapshot is shown as **registered** after confirmation. The verified timetable derives from the authenticated student's block and project academic RPC, not from a static BSIT fixture. Fee and schedule projections are updated after relevant server actions through route revalidation.

The new additive database migration `20261026161225_project_only_section_activation_and_legacy_recovery.sql` was **successfully deployed** and verified with Supabase. The follow-up migration `20261026162558_student_portal_recovery_reason.sql` also deployed and enables the Student Portal to show the Registrar's recovery reason. Local filenames match the migration versions reported by live Supabase. Its two role specific `SECURITY DEFINER` functions are:

1. `project_phase8_activate_ready_sections_v1()` requires the actual authenticated Academic Coordinator. It opens only Phase 8 generated subject sections whose block validation is `READY_PROJECT` and whose schedule is `FINALIZED`; the existing `sections` academic audit trigger records before and after values with the coordinator actor. All institutional and draft sections are excluded. The Coordinator UI has the **Activate Verified Demo Sections** control in the explicit synthetic dataset Sections & Schedules view.
2. `project_phase8_recover_legacy_registration_v1(student_id, reason)` requires the actual authenticated Registrar and a detailed reason. It allows recovery only for a valid confirmed simulated enrollment with no registered subject snapshots, confirmed by a real Registrar in the previous event ledger. In one transaction it records the original confirmation identity and timestamp in `project_phase8_registration_recovery_audit`, appends a `RECOVER_LEGACY` event, and returns the simulation to `RETURNED`. The student must then select real eligible sections and submit again. The Registrar must validate and confirm that new submission before the demonstration COR can be generated. The existing original event history is never removed and the function cannot recover a valid registered record or perform the same legacy recovery twice.

Both functions have denied `anon` access and validate roles from authenticated database identities. The private recovery audit table is RLS protected and denies direct access by browser and service role clients. An unauthenticated live SQL regression demonstrated that both operations correctly refused execution and performed zero changes.

The `sections` and Miguel's historical simulation remained unchanged in the final read-only database verification: 427 `PLANNED`, 0 `OPEN`; Miguel `CONFIRMED_SIMULATION`, 0 saved registered subjects, 0 recovery audit rows. These role actions must be performed with their actual signed-in accounts. A database administrator must not forge a Registrar identity or bypass these record ownership gates merely to remove an error message.
